# 7. Open questions and decisions

## 7.1 Decisions an implementer must make

These are choices the evidence does not settle. Each says what is known and what would settle it. The spec takes no side: the implementer decides, and records the answer in the implementation's own decision log. They are not requirements.

- **DEC-1** - *Master Clear.* The original never writes the slave's Master Clear (`HW-14`) and never forwards the guest's master-clear port write. Whether the missing write causes the unreliable first DMA after load is an open hypothesis: an earlier hardware attempt was inconclusive and a clean run of the planned hardware protocol is outstanding (`TEST-10`). Options include never writing it (as the original), always writing it, or making it configurable (`LIFE-12`). *Considerations:* never writing it reproduces the behaviour that was observed in the emulator and matches the original on any machine where the symptom does not occur. Writing it is untested on real hardware, so its effect on the card (and on a game that already programmed the slave) is not measured. A configurable choice lets the hardware test be run both ways on one build. There is a competing explanation: on an unknown chipset the `setupds` self-test cannot complete its DMA check and may leave the Sound Blaster DSP with a DMA command issued and not finished, so the first real transfer after load would start from that state. That explanation predicts a different remedy (resetting the DSP rather than the slave) and can be told apart by loading the TSR without having run `setupds /s` (a trial outside what `LIFE-2` assumes, not a supported configuration), or by resetting the DSP after load.
- **DEC-2** - *Where settings come from.* The original ignores `ds.ini` and hardcodes its values; `setupds` choices are overwritten. A replacement can keep the defaults (`LIFE-3`), accept a command line (`LIFE-4`), or read back what `setupds` programmed (`LIFE-5`). The last has not been tried. *Considerations:* fixed defaults reproduce the original and keep the TSR small. Command-line options fix the lost-settings problem without reading the card, but users must repeat their `setupds` choices. Reading the card back honours `setupds` automatically, but depends on how reliably those fields can be read once the card is configured.
- **DEC-3** - *Trap architecture.* Stack on VCPI with an own DPMI host (the original), or another way to meet `TRAP-1` to `TRAP-3` (chapter 3, table in 3.3). The first is the only one shown to work for protected-mode programs (three DOS extenders were tested; no real game has been run); it couples the TSR to the memory manager's table layout and has been tested with Jemm only. *Considerations:* the stacked design needs a DPMI host (chapter 4) and hides VCPI from later programs (`TRAP-3`), which is a large part of the build. The alternatives in 3.3 may be smaller but have not been shown to reach protected-mode games.
- **DEC-4** - *How much DPMI.* The measured need is 28 functions (`DPMI-6`); the original has the full 0.9 API. Decide whether to stop at the measured set plus the likely extras (`DPMI-7`) or to add DPMI 1.0 for extenders that want it (`DPMI-10`). *Considerations:* a smaller host means less to build and test, but only three extenders and no real game have been measured (chapter 6, `TEST-12`), so an unmeasured function may turn out to be needed. The original returns "unsupported" for anything outside 0.9 and DOS/4GW tolerates that (`DPMI-8`).
- **DEC-5** - *Which channels.* Fixed hooked channel 1 as in the original, or a configurable one (`EMU-4`). Channels 5-7 (16-bit DMA) have only been read, not run. *Considerations:* a different Sound Blaster DMA setting would need a different channel, and the datasheets describe a per-channel stride in the slave (section 1.3), but the register offset for any channel other than 1 is unknown (section 7.2), so a configurable channel cannot be verified for the others yet.

## 7.2 Things nobody knows yet

Facts about the original that were not established. Some bear on a requirement and are noted there; none prevents building the TSR, but each might matter for compatibility.

- **Whether hooked-channel writes also reach the real 8237.** The guest's writes to the hooked channel are forwarded to the slave. Whether the original also lets them reach the PC's own controller was not established. It decides how the real flip-flop and masks stay consistent, so it bears on `EMU-2` and `EMU-9`.
- **Real-controller side effects of the other register writes.** For Master Clear (0D), Clear flip-flop (0C), Command (08) and Request (09), and for the DMA2 equivalents, it is not established whether the write also reaches the real controller, or which software state the TSR resets. The same goes for reads of the mode, request, temporary and mask registers of the hooked channel (`EMU-13`).
- **Slave status.** Which bit positions of the slave's status register carry terminal count and request, and whether reading it clears terminal count (`EMU-11`).
- **The 16-bit channels (5-7).** The address and count of a 16-bit channel are in words, shifted left one bit on the PC's controller. How the original treats them was not read exhaustively, and no 16-bit channel has been hooked (`EMU-10`, `DEC-5`).
- **Ports C8-CF.** The original has handlers for the channel 6 and 7 address and count ports, but its run showed no trap bits for C8-CF in the memory manager's bitmap. Whether those ports fault is unresolved (`EMU-1`).
- **The manager's own DMA virtualisation.** The original's handler appears to perform the unhooked channels' accesses itself, so a memory manager's own DMA virtualisation (for buffers it has remapped) is apparently bypassed for the trapped ports. Results matched the baseline in the emulator, but a case with a remapped buffer was not run (`TRAP-6`).
- **The layout of the Write-All-Masks byte.** The slave has one mask register at +Fh. The datasheets describe single-channel mask and clear-mask writes as folded into it, but the original's exact bit layout was inferred, not verified (`EMU-12`).
- **A read of the Sound Blaster DSP status port.** One routine in the original's slave-access code reads the register at offset Eh from the Sound Blaster base, which is the DSP's read-buffer status. On a real Sound Blaster this acknowledges an 8-bit interrupt. Its purpose in the original is unclear.
- **Why Dsdma-then-QPIEMU hangs.** Loading the original and then Jemm's QPIEMU makes a V86 DMA probe hang in the emulator. The cause has not been traced (`TRAP-9`).
- **Other INT 67h functions.** After VCPI is hidden, what a design should answer for other INT 67h calls (EMS, for example) is not established (`DPMI-2`).
- **Using VCPI after hiding it.** How a design keeps using the manager's VCPI itself, for example to allocate pages for `DPMI-11`, once later programs are told it is absent, was not established beyond the fact that the original does it.
- **Which PCI device IDs the original accepts.** Only vendor 1073h, device 000Dh has been run (`HW-3`).
- **The slave's per-channel layout.** The datasheets describe a base pointer plus a channel field; the original uses base plus a fixed offset for its one channel (`01-card-interface.md`). Whether other channels would sit at other offsets is unknown because no other channel has been hooked.
- **Extender coverage beyond three.** DOS/4GW, PMODE/W and DOS/32A work. Causeway, other extenders, EMM386, QEMM and real games were not run.
- **Hardware behaviour.** The emulator has no slave. Everything the card does with the values it receives (including what a missing Master Clear does) is untested.
