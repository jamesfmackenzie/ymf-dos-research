# Finding 1 — ndisasm first pass: no Master Clear code path exists at all

**Date**: 2026-10-07
**Method**: raw linear `ndisasm -b 16` over `Dsdma.exe`'s code+data (everything after the
512-byte MZ header, 53,440 bytes). Full output is regenerated by `tools/regen-listings.sh` (to `capture/listings/`) (see `docs/reproducing.md`).
Caveat throughout: this is a flat/unsegmented disassembly of a segmented real-mode binary,
so some regions (e.g. a long run of `CD 30` around file offset `0x3CF0`) are disassembly
desync into data, not real code. Treat anything not corroborated by a clean, sensible
instruction sequence as unreliable until Ghidra's proper segment-aware analysis confirms it.

## Headline result

**There is no code path anywhere in the binary that writes to the D-DMA slave register's
Master Clear offset (`Base + channel + 0xD`).**

Checked exhaustively, not just "didn't spot it while reading": `IN`/`OUT` can only address a
variable port through `DX` on x86, so *every* access to a D-DMA slave register must set `DX`
to `(base variable) + (immediate offset)` right before the instruction. Grepped the entire
disassembly (all 19,962 lines) for every `add dx,0x..` / `add edx,0x..` immediate-add
instruction — the complete set found is `{0x2, 0x4, 0x5, 0x8, 0xb, 0xc0, 0xe, 0xf}`. `0xD`
(Master Clear) and `0x9` (Request register) never appear. This matches the earlier notes' leading
theory for the "first real DMA use after `DSDMA.exe` loads is unreliable, warms up after a
working program runs" bug (Doom demo-end hang, fixed by running Duke Nukem 3D first) — and
sharpens it from "maybe skipped during init" to "there's no code capable of ever doing this
at all," pending Ghidra confirming this isn't disassembly misalignment hiding a code path.

## The accessor library found (file offset ~0x591–0x67D, i.e. ~0xD91–0xE7D from file start
including the 512-byte header)

A tight, clearly hand-written set of subroutines for driving the D-DMA slave registers,
parameterized by two 16-bit base-address variables at data offsets `0x7174` and `0x7176`
(plausibly the two DDMABP-equivalent base pointers for channel groups 0–3 and 5–7, per the
PIIX4 spec — `docs/piix4-ddma-reference.md`) and a mask/selector byte at `0x7179`:

| Function (by first instruction's file offset) | Register offset | Matches PIIX4 table as |
|---|---|---|
| `0x591` | `+5` then `+4`, high byte first, double-read w/ rollover check | Current Word Count (tear-safe read) |
| `0x5B6` | `+1` then `+0` | Current/Base Address read |
| `0x5C6` | `+8`, **merged with hardcoded real port `0x08`** via a mask byte | Status Register read — this is a direct implementation of the datasheet's documented read algorithm: *"PIIX4 uses the data obtained via the read cycles (along with the value in the 8237) to construct the proper data value"* |
| `0x5E6` | `+2` | Page Register read |
| `0x5F4` | `+4` then `+5` (write) | Base Word Count write |
| `0x60A` | `+0` then `+1` (write) | Base Address write |
| `0x61D` | `+2` (write) | Page Register write |
| `0x62F` | `+0xB` (write) | **Mode Register write** |
| `0x641` | `+0xF` (write), with `shr al,2; and al,0xfe` bit-shuffle first | **Write-All-Masks** — the bit-shuffle is consistent with folding a single-channel-mask-style input into the Write-All-Masks bit layout, exactly as the datasheet describes PIIX4 itself doing on the peripheral's behalf |
| `0x658` | reads `[0x7176]+0xE` | unclear — uses the *second* base variable, offset `0xE` isn't in the primary 10-register table at all (see Open questions) |

Covers 8 of the 10 documented register roles (Address, Word Count, Page, Status, Mode,
Write-All-Masks — both directions where applicable). **Missing entirely: Request (`+9h`)
and Master Clear (`+Dh`).**

## VCPI usage confirmed (file offset ~0x00–0x37)

Before any of the above runs, there's a clean V86-monitor-style setup:
```
push ds/es/fs/gs/ss (as data, via push ax after loading ax=0)
mov esi,0 ; mov ebx,esi
mov cx,ss ; movzx ecx,cx ; shl ecx,4 ; add ecx,esp   ; ecx = linear stack address
cli
mov ax,0xDE0C
int 0x67
```
`AH=DEh` is the VCPI signature; `AL=0Ch` is VCPI function `0Ch`, **"Switch from Virtual-8086
mode to Protected Mode."** This directly confirms the earlier notes' existing hypothesis that
`DSDMA.exe` needs "EMM386.EXE-class services" because it uses **VCPI**, not LIM EMS
specifically, to get itself a protected-mode foothold — almost certainly how it later installs
whatever actually traps CPU access to the legacy 8237 ports (the mechanism PIIX4 implements
in hardware via a PCI bus retry; software has no bus to retry on, so it must be trapping the
CPU's `IN`/`OUT` instructions directly via a V86 fault handler instead).

## Real entry point / init logic location

The MZ header's `e_cs:e_ip` (`0x59:0xBCBD`) puts the actual entry point around file offset
`0xC44D` — and there's a dense, clearly-real cluster of `INT 21h` (DOS), `INT 1Ah`
(BIOS/**PCI BIOS** — `AH=B1h` functions, the same mechanism used for the real-hardware
`DEBUG.COM` PCI pokes all session), `INT 67h` (VCPI/EMS), and `INT 2Fh` (multiplex /
presence-check calls) right around file offset `0xAB00`–`0xCD00`. This is almost certainly
the one-time setup routine: detect VCPI, probe for the card via PCI BIOS, parse `ds.ini`,
decide whether to install, then go resident. **Not yet traced in detail** — this is the next
concrete thing to do in Ghidra, since it's where the actual init *order* (and thus whether
Master Clear is simply absent as a primitive, vs. present-but-never-called) gets settled
conclusively.

## Open questions

1. **Offset `0xE` on the second base variable (`0x658`)** — doesn't match any of the primary
   10 register roles. Could be Clear Mask Register (8237 native offset `0Eh`) read back
   through the peripheral for a different purpose, or could belong to a different register
   block entirely (second base variable `0x7176` might not even be the "channels 5–7"
   pointer — needs confirming, not assumed).
2. **Request register (`+9h`) absence** — not just Master Clear is missing; Request is too.
   Worth double-checking whether DSDMA.exe's whole approach (as a *target* of CPU-issued
   writes mimicking the 8237, not as something that issues DMA requests itself) simply never
   needs Request at all — plausible, since Request is for *memory-to-memory* or
   software-initiated DMA, not what a sound card's own hardware triggers.
3. **Disassembly misalignment risk** — this whole pass is a flat linear disassembly of
   segmented code. A real Ghidra project (segment-aware, proper function boundaries) could
   in principle reveal a Master-Clear write hiding inside what currently looks like a data
   region or a misaligned instruction stream. The "no `add dx,0xD` anywhere" result should be
   treated as strong evidence, not 100% proof, until Ghidra corroborates it.

## Next step

Load into Ghidra (GUI or headless), focus first on the `0xAB00`–`0xCD00` init cluster to
trace the actual call order into the accessor library above, and specifically confirm
whether that init routine was ever going to call a Master-Clear-equivalent and simply
can't (because, per this finding, no such accessor exists) — vs. there being a second,
not-yet-found accessor library elsewhere that this flat pass missed.
